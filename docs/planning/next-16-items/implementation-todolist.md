## 2. 产品裁决门禁

### T00｜找工作产品口径确认（覆盖 9）

- 状态：已完成；Owner：产品决策，后续由 `opportunities` 承接；前置：无。
- 需确认：是否迁移参考项目现有杭州/2027 届数据；后台是否同时维护来源和岗位；每日检查是否固定 18:00；哪些管理角色可手动检查；公开页是否保留岗位/来源双视图及六组筛选。
- 澄清方式：按会改变页面定位、数据模型、权限或外部请求行为的问题逐项确认；每个答案写回本项，直到字段、状态、公开/私有边界、管理入口、检查任务和首版非目标均具有唯一口径。
- 裁决 01（页面定位）：采用公开信息与私人求职层结合的模式。公开页面展示客观招聘岗位和官方来源；登录后另行提供个人评级、收藏、投递状态与私人备注。公开岗位事实和用户私有状态必须分开建模、分别授权，私人字段不得进入公开查询、缓存或页面。
- 裁决 02（私人层归属）：私人求职能力面向每个登录用户开放。每位用户独立维护自己的收藏、个人评级、投递状态和私人备注，用户之间完全隔离；后台管理权限不默认赋予查看或修改他人私人求职数据的能力。
- 裁决 03（私人层首版范围）：第一版仅提供用户自己的岗位收藏。个人评级、投递状态、私人备注、下一步日期及求职流程看板均延后，不为未交付能力预建空字段；首版私人事实仅为按“用户 + 岗位”唯一的收藏关联。
- 裁决 04（初始数据）：完整导入参考项目现有的杭州 2027 届数据，覆盖官方来源、已确认岗位、候选岗位、其他历史记录和当前无公开结果记录；导入时已确认保持已确认，候选与其他未确认岗位映射为待确认，当前无公开结果映射为来源状态事实。导入作为带来源标记、可审计的一次性 Labs 初始数据迁移，不把导入时状态声明为实时检查结果；首次真实爬取按裁决 110 更新客观采集字段，正式环境数据迁移仍需单独授权。
- 裁决 05（岗位平等）：不设置企业或岗位等级。参考数据中的 `S/A/B` 层级在导入时丢弃，不进入 schema、后台表单、公开展示、筛选或排序；所有岗位使用同一展示权重，排序不得以主观企业等级裁决。
- 裁决 06（公开核实信息）：公开页面展示岗位核实状态及证据说明。状态仅表示信息是否已确认、是否符合目标届别/类型或官方来源当前是否有公开结果，不表达岗位质量或推荐等级；证据必须是适合公开展示的事实摘要，不得包含私人备注或内部错误详情。
- 裁决 07（后台管理范围）：后台同时管理官方来源和具体岗位。获授权管理员可分别新增、编辑、停用来源，以及新增、编辑、上下架岗位；岗位可关联一个官方来源。来源爬虫可以按自动入库规则创建或更新岗位的客观采集字段，并可按自动过期规则推动岗位状态变化；管理员仍独占核实状态修正、公开证据修正和上下架决定。自动过程不得覆盖管理员维护字段。
- 裁决 08（管理与检查权限）：仅唯一管理员可以查看招聘管理后台、创建/编辑/停用来源、创建/编辑/上下架岗位，以及执行单项或批量来源检查。作者身份不附带招聘管理或外部请求权限；作者和普通用户只能读取公开事实，登录用户另可管理自己的收藏。管理写入与手动检查均需独立服务端权限、CSRF、频率限制和审计。
- 裁决 09（自动检查时间）：按 `Asia/Shanghai` 每天 18:00 自动检查全部启用来源，接入现有 Celery/TaskRun 调度和观测。定时与管理员手动检查调用同一安全、幂等服务；同一来源同一时刻至多一个检查任务。检查服务可依据已确认的连续失败或岗位链接失效规则自动推动关联岗位进入“已过期”，其他岗位字段不被自动改写。
- 裁决 10（公开主视图）：公开端保留“岗位记录 + 官方来源”双视图，默认进入岗位列表。来源视图展示官方入口及适合公开的最近检查状态和时间，允许访客核对信息来源；安全错误详情、完整检查历史和管理动作仍仅在唯一管理员后台可见。
- 裁决 11（岗位筛选）：公开岗位列表提供关键词搜索，以及城市、核实状态、企业、招聘类型、岗位类别、届别六项筛选。筛选由服务端查询裁决并保留在 URL，HTMX 只负责局部更新；登录用户在同一筛选区域额外获得“仅看收藏”，未登录用户不显示该私有筛选。
- 裁决 12（默认岗位筛选）：岗位视图首次进入时自动选中管理员配置的城市、核实状态、企业、招聘类型、岗位类别、届别六组默认筛选标签；初始核实状态为“已确认”和“待确认”，其中“候选”统一为“待确认”。这些默认值只是普通筛选项，用户可以直接取消或改选，不存在“默认范围/非默认范围”属性或独立筛选组。“当前无公开结果”不是具体岗位，完整导入时将这类记录转为对应官方来源的状态事实并展示在来源视图，不创建伪岗位。
- 裁决 13（停用与历史）：来源使用可恢复的停用，岗位使用可恢复的下架，不在普通管理动作中物理删除。公开列表默认隐藏停用来源和下架岗位；用户已有岗位收藏继续保留并标记“已下架”，不得级联删除。管理员可查看历史、恢复并审计状态变化。
- 裁决 14（默认排序）：公开岗位按企业名称、岗位名称稳定排序，相同值再用稳定 ID 收口；不按更新时间、核实状态、收藏数或人工位置表达推荐关系。所有筛选结果和分页使用同一确定性顺序。
- 裁决 15（岗位打开方式）：不新增本站岗位详情页。岗位列表项直接承载企业、岗位、地点、招聘类型、岗位类别、届别、核实状态、公开证据和收藏动作；点击岗位标题在新标签页打开官方岗位 URL，并使用明确的外链提示与 `noopener noreferrer` 安全属性。
- 裁决 16（未登录收藏）：公开列表始终展示收藏操作。未登录用户点击时跳转登录，登录成功后回到原岗位列表的视图、筛选条件和分页；登录用户在原位完成收藏或取消收藏，成功反馈复用现有非阻塞提示，列表不因按钮文案或状态变化产生布局跳动。
- 裁决 17（公开入口）：采用组合入口。岗位列表作为主页侧边导航中可配置的“找工作”项，同时在顶部“我的文章”和通知操作旁新增独立的“工作”入口；两处使用同一稳定 URL 和同一页面，不建立平行路由。顶部入口沿用现有紧凑图标按钮与悬停说明，侧边入口继续受现有导航编排控制。
- 裁决 18（默认筛选配置）：页面定位为通用“工作机会”，不把杭州、2027 届或技术方向写死在页面、数据模型或公共 URL 中；管理员可在工作机会设置中配置与公开岗位页一致的城市、核实状态、企业、招聘类型、岗位类别、届别六组多选默认值，作为进入岗位列表时的初始勾选项。所有筛选项都是公开页面的普通条件，访客可主动调整或清除；完整导入的杭州 2027 届技术招聘数据仅为首批内容，不限制后续维护范围。
- 裁决 19（默认筛选生效）：仅当用户直接进入岗位列表且 URL 不含任何筛选参数时，预选管理员配置的默认筛选标签。用户主动调整或清除筛选、浏览器历史恢复、以及任何带筛选参数的链接均以 URL 为唯一事实，不被站点默认值覆盖。
- 裁决 20（岗位类别与搜索）：不新增管理员维护的“方向”字段。岗位类别从各官方来源公开页面可见的筛选项中受控采集、规范化并去重，形成可供用户使用的类别筛选集合；管理员需为每个来源明确可采集的类别入口，未提供可安全读取筛选项的来源不推测类别。岗位以标题、招聘计划和公开证据中的关键词匹配关联到类别；关键词搜索与类别筛选独立，直接匹配岗位的公开可检索字段。类别采集属于受限外部读取能力，必须使用与来源检查相同的 HTTPS、域名 allowlist、重定向重判、超时、响应大小、幂等、审计和安全错误约束，不能以通用页面爬取或浏览器脚本兜底。
- 裁决 21（城市筛选集合）：城市筛选与岗位类别采用同一来源采集策略。管理员为每个来源配置公开城市筛选入口，系统受控读取、规范化并去重后汇总为公开城市选项；岗位原始地点文本仍作为岗位事实保存，不用未经验证的地点文本反推城市集合。城市采集与类别采集共享安全边界、任务幂等和审计，不建立第二套爬虫。
- 裁决 22（采集选项历史）：来源不再提供的城市或岗位类别保留历史身份并标记当前不可用，不删除已有岗位关联或用户收藏；公开筛选默认只展示当前可用选项，管理员可查看历史选项及其最后发现时间。重新发现同一规范值时恢复可用状态，状态变化留审计。
- 裁决 23（选项规范化）：城市和岗位类别只做保守规范化：去除首尾空格、统一连续空白、统一大小写和常见标点后去重；不做语义合并或猜测映射，“杭州/滨江”与“杭州”、“后端开发”与“后端”等不同来源值分别保留。
- 裁决 24（采集失败）：来源的城市/类别采集失败时保留上次成功的岗位关联和筛选集合，并将采集结果标记为过期、记录最后成功时间与本次安全错误码；不得清空或伪造新数据。失败通过现有通用通知接口发送给唯一管理员并进入通知中心，通知只包含来源、失败阶段、安全错误摘要和最后成功时间，不包含响应正文、凭据、Cookie 或堆栈。
- 裁决 25（采集通知频率）：正常检查或采集成功不发送通知；首次失败、进入过期状态或达到明确的重试/过期阈值时按来源与失败阶段去重通知唯一管理员。来源从失败/过期恢复为成功时发送一次恢复通知；持续失败不重复刷屏，但后台保留当前状态和完整检查历史。
- 裁决 26（企业事实）：企业名称由官方来源统一维护，岗位必须关联来源并自动继承企业展示值；岗位不重复保存企业字段，也不允许岗位与来源产生不一致。来源企业改名后，关联岗位列表和筛选读取同一最新来源事实，历史审计保留变更记录。
- 裁决 27（岗位来源关系）：每个岗位只允许关联一个唯一官方来源。同一企业的不同招聘入口分别建为独立来源，岗位不做多来源聚合或补充链接；来源归属、企业展示值和检查状态均由该唯一来源裁决。
- 裁决 28（岗位字段边界）：管理员手动新增岗位时必须填写唯一来源、岗位标题、岗位 URL、招聘类型、岗位类别、届别、城市/地点和公开证据；新建入口不允许直接指定已确认状态。岗位进入编辑或审核阶段后，管理员才可修正公开证据、核实状态和上下架决定。爬虫自动创建岗位时先写入可验证的客观采集字段和来源快照。岗位不要求复制完整职位描述，也不要求额外发布时间字段；校验、审计和公开 DTO 均以这组字段边界为准。
- 裁决 29（岗位核实状态）：岗位核实状态固定为 `已确认`、`待确认`、`已过期` 三种枚举；“当前无公开结果”只属于来源检查状态，不创建岗位状态。默认城市、届别等筛选配置不改变岗位状态，也不产生额外范围属性；核实状态不得由自由文本扩展，变更需经岗位服务、权限和审计。
- 裁决 30（自动过期）：来源检查失败或岗位链接失效可以自动将关联岗位标为“已过期”，但不得覆盖岗位标题、类别、届别、地点、证据等其他字段；自动状态变化必须记录触发检查、失败阶段/安全错误码和审计事件，恢复条件另行确认。
- 裁决 31（过期阈值与公开隐藏）：同一来源或岗位链接按每日 `18:00 Asia/Shanghai` 检查周期累计连续失败次数。首次失败只记录异常、保留岗位公开展示；下一日再次失败即累计第二次并自动将岗位标为“已过期”，从公开岗位列表隐藏，但保留后台历史、用户收藏和恢复能力。任意一次成功会清零连续失败计数并按后续恢复规则处理。
- 裁决 32（过期恢复）：已过期岗位下一次检查成功后自动恢复为“待确认”并重新公开；不得自动恢复为“已确认”。管理员可根据新的公开证据再次确认，状态变化和触发检查均保留审计。
- 裁决 33（双 URL 检查）：来源 URL 与岗位 URL 分开检查。来源检查只裁决招聘入口的可达性、最终 URL、HTTP 状态和页面标题；岗位检查单独裁决具体岗位链接的可达性，并按连续失败规则推动该岗位过期或恢复。来源入口成功不替代岗位链接检查。
- 裁决 34（岗位检查范围）：每日 `18:00 Asia/Shanghai` 自动检查全部启用岗位的岗位 URL，同时检查全部启用来源 URL；检查范围不受管理员默认筛选或公开页面当前筛选条件影响，避免用户筛选导致岗位长期无人维护。任务按资源预算实行受限并发、速率控制、幂等和可观测重试。
- 裁决 35（岗位失败判定）：岗位 URL 检查中，HTTP `404/410`、连接/读取超时、网络错误和 `5xx` 均计为一次失败，并记录可公开安全的错误类型；`3xx` 不直接计为失败，必须按每跳 allowlist、HTTPS、DNS/私网重判和重定向上限完成最终判定。连续两次失败才自动过期，单次失败保持岗位可见。
- 裁决 36（岗位成功判定）：岗位 URL 经安全重定向后最终响应为任意 `2xx` 即算链接检查成功；最终非 `2xx` 按失败类型累计。检查不以页面正文是否包含岗位标题作为成功前提，避免依赖脆弱的页面文案匹配。
- 裁决 37（岗位域名边界）：岗位 URL 必须属于其唯一来源配置的允许 HTTPS 域名列表；允许来源明确配置的多个合法域名及其安全重定向，但每次请求和重定向后的域名都必须重新通过 allowlist、HTTPS、DNS/私网和保留地址检查，超出列表即拒绝并记录安全错误。
- 裁决 38（allowlist 维护）：保存来源时系统从来源 URL 的规范 host 自动推导初始允许域名，唯一管理员可以在来源管理表单中追加、删除或调整 allowlist；保存岗位 URL 和每次实际请求前都重新校验。DNS、重定向或响应内容发现的新域名不得自动加入信任边界，超出 allowlist 的地址直接拒绝并审计。
- 裁决 39（来源类型与爬虫）：来源类型使用固定枚举，例如校园招聘、实习招聘、社会招聘、官方综合招聘和其他，不允许任意自由文本扩展。所有招聘来源都必须登记为可管理的官方岗位列表界面，每个来源绑定明确的爬虫适配配置，负责受控读取该列表及其公开筛选项；来源不是单纯 URL 记录。爬虫自动入库遵循裁决 40，并复用统一的 HTTPS、allowlist、DNS/私网重判、超时、响应大小、重试、幂等、审计和通知边界。
- 裁决 40（爬虫自动入库）：来源爬虫读取到结构化岗位后自动创建或更新岗位。自动写入仅限来源快照、岗位 URL、标题、招聘类型、来源类别/城市、届别、地点和采集时间等客观字段；新岗位初始核实状态为“待确认”并立即公开，进入管理员审核队列；管理员审核不通过时可下架或改为其他核实状态。管理员维护的核实状态、公开证据、上下架和人工修正字段不得被后续爬虫覆盖。创建、更新、跳过和冲突均需幂等、可追溯并留安全审计。
- 裁决 44（审核不通过）：管理员审核岗位时，不以页面当前默认筛选或用户筛选作为岗位状态依据；管理员可修正岗位城市/届别或独立决定是否下架，不新增“审核驳回”枚举；审核原因和公开证据保留。
- 裁决 45（爬虫适配器配置）：招聘来源只能选择系统内置、版本化的爬虫适配器；管理员填写来源 URL、allowlist 和该适配器定义的筛选入口配置。后台不接受任意 CSS/XPath/JSONPath、脚本或模板执行规则，避免配置形成第二解析系统和代码执行边界。
- 裁决 46（适配器解析失败）：内置适配器无法解析来源时保留上次成功的岗位、城市和类别结果，停止本次来源的岗位更新，不写入不确定数据，也不删除现有岗位；按通用通知去重规则通知唯一管理员。适配器修复并重新成功后，才继续自动入库和差异处理。
- 裁决 47（爬虫自动更新字段）：爬虫只更新岗位 URL、标题、招聘类型、来源类别、来源城市、届别、地点、来源快照和采集时间等客观来源字段；管理员曾修改的公开证据、核实状态、上下架状态和类别覆盖永久优先，自动任务只能记录差异供审核，不能覆盖人工值。
- 裁决 48（自动证据摘要）：新岗位自动入库时由爬虫生成结构化公开证据摘要，至少包含来源名称、来源列表 URL、抓取时间和岗位列表中的可验证字段；不保存完整页面正文、脚本、Cookie 或响应原文。管理员后续补充/修正的公开证据永久优先，爬虫只记录新快照差异。
- 裁决 49（岗位类别/城市覆盖）：管理员可以覆盖单个岗位的公开岗位类别和城市，同时保留爬虫原始采集值；公开列表和筛选使用人工覆盖值，人工值永久优先，覆盖动作进入审计。全局城市/类别选项集合仍只来自来源采集，单个岗位覆盖不会隐式创建新的全局选项。
- 裁决 50（爬虫审核队列）：后台提供统一审核队列，汇总爬虫新建岗位和已有岗位的字段变化；管理员可逐条接受爬虫值、保留人工值、修正核实状态或下架。队列是自动入库并立即公开后的事后校验与纠偏入口，不作为发布前置门禁；每次处理记录差异、选择、actor 和审计时间。
- 裁决 51（审核批量操作）：审核队列支持逐条处理和批量接受低风险客观字段变化；批量动作必须展示精确数量和字段范围并使用共享确认交互。保留人工值、修改核实状态、下架等高影响决定仍需逐条确认，不提供批量下架或批量状态裁决。
- 裁决 52（来源列表缺失）：岗位连续两次未出现在来源列表中，但岗位 URL 检查仍为最终 `2xx` 时，不自动过期或隐藏；保留公开岗位并标记“来源列表缺失”，生成审核队列项并按去重规则通知管理员。只有岗位 URL 自身达到连续失败阈值才自动进入“已过期”。
- 裁决 53（列表缺失可见性）：“来源列表缺失”仅在管理员后台、审核队列和安全通知中展示，不进入公开岗位 DTO。公开端继续展示原核实状态和最后核实时间，不因列表缺失自动降为“待确认”或展示内部爬虫差异。
- 裁决 54（最后核实时间）：公开岗位列表的“最后核实时间”取该岗位 URL 最近一次成功检查的完成时间，直接表达具体链接何时最后确认可访问。来源列表最近抓取时间不替代岗位时间，只在官方来源视图和管理员后台展示。
- 裁决 55（分页数量）：岗位列表复用全站统一的每页数量选项和选择后立即生效的交互，不建立岗位专属分页偏好。未登录访客使用全站默认值，登录用户使用既有账户偏好；翻页始终保留当前视图、搜索和筛选 URL 参数。
- 裁决 56（来源公开排序）：官方来源视图按企业名称、固定来源类型稳定排序，相同值再用稳定 ID 收口；不按异常状态、最近检查时间或人工位置表达推荐关系。管理员后台可单独筛选异常/过期来源，但不改变公开默认顺序。
- 裁决 57（来源公开字段）：官方来源视图展示企业、固定来源类型、官方入口、最近一次成功检查时间、当前安全状态和当前公开岗位数量；岗位数量只统计公开可见岗位。内部错误码、连续失败次数、审核差异、爬虫配置和完整检查历史仅在管理员后台可见。
- 裁决 58（来源公开状态）：公开来源状态固定映射为“正常”“暂时异常”“信息过期”“已停用”四种用户文案，由来源启用状态、当前检查结果、连续失败/过期阈值和最后成功时间统一计算；公开端不展示 HTTP 状态码、异常消息或内部错误原因。
- 裁决 59（停用来源公开性）：停用来源默认从公开来源视图完全隐藏，只在管理员后台和历史中保留；停用不物理删除关联岗位历史或用户收藏。“已停用”状态保留为管理/读回语义，不作为默认公开列表项。
- 裁决 60（停用来源级联）：停用来源时自动下架其全部关联岗位，并为每个岗位保存来源停用前的精确上下架状态；恢复来源时只恢复原本在架的岗位，原先已下架岗位继续下架。整个动作需事务一致、审计并精准失效公开缓存；用户收藏不删除并显示“已下架”。
- 裁决 61（检查历史保留）：来源和岗位 URL 的逐次检查明细保留 90 天，之后由现有任务系统有界、幂等清理；当前状态、连续失败计数、最后成功时间和引发岗位过期/恢复、来源状态变化的审计事实长期保留。历史清理不得改变当前公开状态或用户收藏。
- 裁决 62（爬虫快照保留）：爬虫快照只保存结构化摘要 90 天，包括本次岗位身份集合、字段哈希、城市/类别集合和与上一成功快照的差异；不保存原始 HTML、脚本、响应正文或 Cookie。长期事实由岗位、来源、当前状态和审计承担，快照到期后有界、幂等清理。
- 裁决 63（审核摘要通知）：每次来源爬虫任务完成后，若存在待审核变化或失败，通过现有通知中心向唯一管理员发送一条合并摘要，包含新增岗位、字段变化、来源列表缺失和失败数量，并链接到该任务对应的审核队列筛选；不按岗位逐条通知。无变化且无失败时不通知，重复任务按任务/结果版本去重。
- 裁决 64（JavaScript 来源采集）：内置适配器默认使用普通 HTTP；只有确实依赖 JavaScript 的来源可由适配器显式声明受限无头浏览器模式，必要时使用 Playwright。Playwright 只能由版本化适配器和专用爬虫任务调用，不复用开发验收浏览器、不接受管理员脚本；必须单实例、受资源预算约束、限时限内存、禁止下载/上传/持久会话，并对主文档、子资源和每次重定向执行 HTTPS、allowlist、DNS/私网与保留地址重判，不得作为通用失败 fallback。
- 裁决 65（登录来源）：第一版只支持无需登录即可查看的官方公开招聘页面。系统不保存或使用招聘平台账户、密码、验证码、Cookie、storage state 或其他登录会话；需要登录的来源标记为“暂不支持自动采集”，不得要求管理员上传凭据或会话。
- 裁决 66（岗位搜索字段）：公开搜索框在服务端模糊匹配岗位标题、来源企业、招聘计划、城市/地点、公开岗位类别、届别和公开证据，并与六组筛选组合。搜索不得匹配内部快照、安全错误、审核记录、allowlist 或 URL，不将私有/内部字段泄漏为命中依据。
- 裁决 67（搜索排序）：存在搜索词时先按已确认公开字段的匹配相关度降序，再按企业名称、岗位名称和稳定 ID 收口；没有搜索词时继续使用企业名称、岗位名称、稳定 ID 的默认顺序。相关度不得使用收藏数、用户私有数据或内部审核字段。
- 裁决 68（公开摘要计数）：公开页面摘要展示公开岗位总数、已确认岗位数、待确认岗位数和启用官方来源数；计数不包含下架/已过期岗位、停用来源或用户私有收藏。当前搜索/筛选结果数量在列表标题处独立展示，不替换全局摘要。
- 裁决 69（收藏查看入口）：登录用户只在工作页面通过“仅看收藏”筛选查看自己的岗位收藏，不在账户中心新增独立岗位收藏页面。收藏按钮、收藏筛选和下架收藏提示共享同一按“用户 + 岗位”唯一的私有事实。
- 裁决 70（失效收藏）：登录用户启用“仅看收藏”时包含自己已收藏的下架和已过期岗位，并明确标记“已下架”或“已过期”；这些岗位仍不进入普通公开列表。用户可取消收藏，但收藏查询不得暴露来源内部错误、审核差异或其他后台字段。
- 裁决 71（岗位招聘类型）：爬虫从岗位事实中提取招聘类型并映射到固定枚举，管理员可对单个岗位覆盖；综合招聘来源中的不同岗位可有不同类型，不强制继承来源类型。枚举首版包含校园招聘、实习招聘、社会招聘、应届生招聘和其他；无法可靠映射时使用“其他”并保持“待确认”，不以自由文本扩展枚举。
- 裁决 72（岗位届别，2026-08-14 修订）：爬虫可以从来源文本提取届别，统一采集入口只接受上海招聘学年中的当届与下一届纯年份标签；每年 `1-6` 月保留当年和次年，`7-12` 月切换为次年和后年，例如 `2026-08` 只保留 `2027届、2028届`。明确的非年份届别及窗口外岗位不自动入库或更新；来源没有公开届别时保留岗位并让届别为空，不猜测年份；多届岗位只保留窗口内届别。管理员手动维护岗位及届别覆盖不受该爬虫窗口限制。
- 裁决 73（默认届别选择）：管理员只能从当前可用届别集合中选择一个默认届别，不接受自由文本或多选。默认届别后来不可用时，公开页停止自动应用该默认值并回到无届别默认筛选；通过现有通知中心提示唯一管理员重新选择，历史配置和变化保留审计。
- 裁决 74（默认城市选择）：管理员只能从当前可用城市集合中选择一个默认城市，不接受自由文本或多选。默认城市后来不可用时，公开页停止自动应用该默认值并回到无城市默认筛选；通过现有通知中心提示唯一管理员重新选择，用户仍可主动选择其他城市或清除筛选。
- 裁决 75（筛选多选）：城市、岗位类别、企业、招聘类型、届别和核实状态六组筛选全部支持多选；同组值使用 OR，不同组之间使用 AND，并与关键词搜索和“仅看收藏”组合。URL 以重复参数或等价结构化方式保存全部选中值，服务端验证、规范化、排序并裁决查询和浏览器历史。
- 裁决 76（筛选即时生效）：任一筛选勾选、取消或清除后立即通过 HTMX 局部刷新岗位结果、当前结果数和分页，不提供“应用筛选”按钮；更新状态显示在筛选标题旁，页面不整页闪烁、不改变当前滚动位置。快速连续选择取消或合并旧请求，防止陈旧响应覆盖，URL 和浏览器历史同步。
- 裁决 77（筛选折叠态）：岗位筛选区域在桌面和手机均默认折叠，标题旁展示当前有效筛选数量/摘要；展开后显示搜索和六组多选。折叠/展开只属于当前页面 UI 状态，不成为服务端筛选真值；没有任何用户有效条件时不显示“清除筛选”操作。
- 裁决 78（搜索触发）：搜索框只在按 Enter 或点击搜索按钮时提交，不在每次输入时自动请求。提交后保留六组筛选与“仅看收藏”，将页码重置为第一页，通过局部刷新更新结果和 URL；输入文字本身不得触发页面滚动或请求。
- 裁决 79（岗位搜索入口）：工作页面使用独立岗位搜索框，只匹配已确认的岗位公开字段；顶部全站搜索继续只负责文章/作者，不增加岗位类型，也不与岗位筛选状态双向同步。岗位搜索参数属于工作页面自己的稳定 URL 契约。
- 裁决 80（岗位列表布局）：桌面端使用紧凑表格，支持扫描企业、岗位、招聘类型、类别、城市/地点、届别、核实状态、最后核实时间和操作；移动端转换为单列条目，不强制横向表格，也不提供表格/卡片切换。公开证据摘要在条目内按需展开，避免默认行高失控。
- 裁决 81（证据展开）：公开证据在当前岗位行/移动条目内折叠展开，默认只显示简短摘要；展开与收起不导航、不改变外层页面滚动位置，也不在页面其他区域渲染内容。触发器提供明确的展开状态、键盘操作和焦点保持。
- 裁决 82（岗位操作列）：桌面表格最右侧使用稳定宽度操作列，放置收藏和证据展开图标按钮；按钮只显示图标并提供可访问名称/tooltip，收藏实心状态切换不改变列宽或行高。移动端在条目底部使用固定动作区，点击目标至少 44px。
- 裁决 83（来源列表布局）：官方来源视图使用独立紧凑表格，按企业、来源类型、官方入口、当前状态、最近成功检查时间和公开岗位数分列；移动端转换为单列条目。它与岗位表格共享页面宽度、分页和响应式基础组件，但保持自己的列定义和语义，不强行共用同一 DOM 表格。
- 裁决 84（双视图状态）：岗位与官方来源视图各自独立保留自己的搜索、筛选和分页 URL 参数；切换后恢复该视图上次的条件，不共享页码，也不把岗位筛选误用于来源。浏览器前进/后退按完整 URL 恢复视图和条件，局部更新不改变页面滚动位置。
- 裁决 85（来源分页采集）：爬虫采集来源全部可达分页或无限滚动结果，但受系统级单来源最大页数、最大岗位数和总时间上限约束；达到任一上限即将本次结果标记为“截断”，保留已采集数据并通知管理员。截断结果不得用于判定未出现岗位为“来源列表缺失”、过期或删除。
- 裁决 86（来源采集软上限）：管理员可为每个来源配置单次最大页数、最大岗位数和总时间软上限；未配置时默认 `50` 页、`5000` 个岗位、`10` 分钟。来源配置不得突破系统硬上限；达到软上限仍按“截断”结果处理，不作为完整快照。
- 裁决 87（系统采集硬上限）：系统不可突破的单来源页数、岗位数和总时间硬上限不预设拍板，实施时在隔离 Labs 环境按真实 HTTP 与 Playwright 适配器、现有服务负载和资源预算完成单 worker 压测后确定。硬上限不得低于默认软上限，也不得由管理员覆盖；压测结果、选择依据和运行值写入测试/运维文档，未完成门禁前不开放大于默认值的来源配置。
- 裁决 88（每日任务串行）：每天 18:00 的自动任务按来源串行执行，一次只处理一个来源；单个来源内部也不得并发启动多个 Playwright。每个来源列表采集完成后再检查其岗位 URL，避免叠加重型任务；单个来源失败、截断或不支持不阻断后续来源，最终 TaskRun 汇总成功、失败、截断与跳过数量。
- 裁决 89（全量检查幂等）：管理员点击“检查全部来源”时，如已有自动或手动全量任务运行，不创建、排队或取消第二个任务，直接返回当前 TaskRun 并展示同一进度/结果入口。全量检查在系统范围同一时刻至多一个运行实例，重复点击保留审计但不重复外部请求。
- 裁决 90（全量运行时的单来源检查）：全量任务运行时，管理员点击单个来源“立即检查”，若当前正处理该来源则复用当前来源进度；否则拒绝创建、插队、排队或并发任务，并提示等待全量任务完成。系统重型爬虫槽位和同一来源始终只有一个运行者。
- 裁决 91（全量检查取消）：唯一管理员可以请求安全取消全量检查；当前来源完成正在执行的原子步骤后停止，已提交来源结果保留，未处理来源标记“未执行”，当前未提交快照不落库。TaskRun 进入 `CANCELLED` 并汇总完成、失败、截断、跳过和未执行数量；不得强杀浏览器或留下半个来源事实。
- 裁决 92（管理导航结构）：管理后台增加一个“工作机会”一级导航项，内部使用“审核队列、岗位、来源、任务历史、设置”五个标签页，默认进入审核队列；五页共享唯一管理员权限 owner。存在待审核项或失败/过期任务时，一级导航和对应标签使用现有管理导航的流动提醒效果，不建立第二通知状态。
- 裁决 93（后台岗位筛选）：后台“岗位”页提供关键词搜索，以及核实状态、上下架、企业/来源、招聘类型、类别、城市、届别和创建来源（爬虫/人工）筛选；后台查询独立于公开 URL，可查看下架、已过期、来源列表缺失和人工/爬虫差异状态。筛选和分页仍由服务端裁决并保留在后台 URL。
- 裁决 94（后台来源筛选）：后台“来源”页提供企业/URL 搜索，以及启用状态、固定来源类型、内置适配器、当前检查状态、信息过期、结果截断和暂不支持自动采集筛选；默认仍按企业名称、来源类型和稳定 ID 排序。异常维度只用于管理员定位运维问题，不进入公开查询参数。
- 裁决 95（新来源启用流程）：新来源默认保存为停用草稿，不进入公开来源视图、不启动爬虫或岗位自动入库；管理员核对 URL、allowlist、内置适配器、筛选入口和软上限后显式启用。启用事务提交后立即触发首次检查；首次失败时来源保持启用但显示异常并按去重规则通知管理员，不伪装为启用成功即采集成功。
- 裁决 96（来源首次公开）：新来源启用后，在首次来源检查与岗位列表解析成功前仍只在管理员后台可见；首次成功后自动进入公开来源视图，并开始公开其自动入库岗位。首次失败或截断不公开来源，也不把部分结果当成首个完整公开基线。
- 裁决 97（首批岗位公开）：首次完整爬取成功与后续爬取使用同一自动入库规则；来源首次公开时，首批新岗位立即以“待确认”状态公开并进入审核队列，不增加首批批量确认门禁。失败或截断结果不能公开来源或首批部分岗位。
- 裁决 98（参考来源适配覆盖）：第一版必须逐一处理参考项目中的全部招聘来源。每个来源要么绑定可工作的内置适配器并通过真实公开页面采集验证，要么以停用/“暂不支持自动采集”记录明确保存不可支持原因；不得静默遗漏、伪装成功或用通用解析 fallback。首版验收需列出全部来源、适配器、验证结果和不支持原因。
- 裁决 99（来源与岗位状态优先级）：来源列表连续失败只将来源标为“信息过期”，不级联改变关联岗位核实状态；具体岗位 URL 最近检查仍为 `2xx` 时继续公开并保持原状态。只有岗位 URL 自身连续两次失败才自动将该岗位标为“已过期”并隐藏，来源异常不能替代岗位检查结果。
- 裁决 100（岗位多类别）：一个岗位可关联多个岗位类别，不设主类别；爬虫关键词匹配和管理员覆盖均产生类别集合。公开筛选中，岗位命中用户选中的任一类别即可通过该类别组，类别组再与其他筛选组 AND；桌面表格和移动条目以紧凑标签展示全部公开类别并受控换行。
- 裁决 101（岗位多城市）：一个岗位可关联多个规范城市，用户选中任一关联城市即可命中该城市组；岗位原始地点文本继续完整展示。爬虫从来源公开城市选项及岗位关联生成城市集合，管理员可覆盖；不得把多城市岗位强制压成一个筛选城市或只依赖原始地点文本搜索。
- 裁决 102（岗位多届别）：一个岗位可关联多个规范届别，用户选中任一关联届别即可命中该届别组；爬虫提取和管理员覆盖都使用届别集合，不把多个届别合并成不可筛选的组合值。来源原始届别文本保留在结构化采集摘要中用于差异和审计。
- 裁决 103（历史记录修订）：此前将“非默认范围”建模为查询属性的口径作废。原“非目标届别/类型”记录只按真实岗位字段导入为待确认岗位或来源状态事实，不生成“默认范围/非默认范围”状态、字段、标签或筛选组。
- 裁决 104（默认筛选而非范围）：岗位只持久化“已确认/待确认/已过期”核实状态。管理员配置的默认城市、默认届别等只是公开页面首次进入时自动勾选的普通筛选项；查询不计算额外范围属性，修改默认配置也不批量更新岗位行。
- 裁决 105（筛选组修订）：公开岗位页不增加“默认范围内 / 非默认范围”筛选组。公开筛选组为城市、核实状态、企业、招聘类型、岗位类别、届别六组，全部是用户可以直接取消或改选的普通多选条件。
- 裁决 106（首次默认筛选）：用户以无筛选参数 URL 首次进入岗位页时，预选当前有效的管理员默认筛选标签，并将这些普通筛选值写入规范 URL；用户之后清除、调整或改选时不再由站点默认值覆盖。默认值缺失或不可用时不自动补选对应组，仍按用户可见的其他条件查询。
- 裁决 107（默认筛选组合）：用户改选默认标签后，城市、届别及其他筛选继续按同组 OR、组间 AND 组合；系统不自动清除或禁用其他条件。组合无结果时展示诚实空状态和有效清除操作。该裁决替代此前关于“非默认范围”组合的记录。
- 裁决 108（来源视图筛选）：官方来源视图提供企业/来源名称搜索和来源类型筛选。搜索与筛选只作用于来源视图，和岗位视图的条件、页码、URL 参数相互独立；来源视图继续保留自己的分页和空状态。
- 裁决 109（管理员手动新建岗位）：唯一管理员手动新建岗位后，系统固定以“待确认”状态立即公开，并同时创建审核队列项；创建权限不等于审核通过，不能在新建表单中直接设为“已确认”。后续由管理员在审核队列中确认、修正或下架，所有变化继续通过岗位 service 和审计记录。
- 裁决 110（导入后的首次爬取）：参考项目数据导入后，首次完整成功的真实爬取可以按正常自动更新规则刷新岗位 URL、标题、招聘类型、来源类别/城市、届别、地点、来源快照和采集时间等客观字段；管理员已维护的公开证据、核实状态、上下架状态及人工覆盖值继续永久优先。客观字段差异需保留前后值并进入审核队列，导入来源和首次爬取批次均可审计，不以整行替换覆盖导入记录。
- 裁决 111（robots.txt 策略）：每个来源保存独立的“遵守 robots.txt”配置，默认开启；普通 HTTP 与 Playwright 适配器都必须读取并遵守目标站点规则。只有唯一管理员在来源设置中显式关闭后，该来源才允许忽略 robots.txt；关闭操作必须显示明确风险提示、记录 actor/来源/前后值和时间审计，且不得顺带放宽 HTTPS、allowlist、DNS/私网重判、重定向或资源上限。来源未配置、迁移旧数据或配置读取失败时均按“遵守”处理。
- 裁决 112（同域请求间隔）：爬虫对同一规范域名的连续请求默认至少间隔 `2` 秒；唯一管理员可按来源把间隔调大，但不能低于系统默认值。普通 HTTP、Playwright、分页、岗位 URL 检查和重试共享同一限速 owner，重定向后的目标域名按各自域名限速，任何适配器不得绕过。来源未配置或配置读取失败时使用 `2` 秒；间隔变更记录审计，并与来源串行和单 worker 约束同时生效。
- 裁决 41（岗位幂等身份）：爬虫使用“唯一来源 + 规范化岗位 URL + 规范采集标题”作为岗位唯一身份，允许同一来源列表 URL 下多个标题不同的独立岗位。规范采集标题只做 NFKC、连续空白收敛和大小写归一，不做模糊或语义合并；管理员覆盖公开标题或公开 URL 不改变稳定采集身份。同一复合身份重复读取时更新原岗位；采集 URL 或规范采集标题真实变化视为新岗位，旧岗位保留历史并按既有缺失/过期/下架规则处理。
- 裁决 42（岗位 URL 规范化）：岗位身份使用保守规范化 URL：统一 scheme/host 大小写、移除默认端口、规范路径，并只移除固定且经代码审查的无业务意义追踪参数；业务 query 参数和 fragment 保留。追踪参数名单不得由外部输入或运行时猜测，规范化前后值需可审计。
- 裁决 43（人工字段优先）：管理员手动修改过的岗位标题、类别、届别、地点、公开证据、核实状态和上下架状态永久优先，后续爬虫不得覆盖。爬虫只维护客观采集字段、来源快照和最新抓取值；抓取值与公开采用值不一致时保留差异记录供管理员查看和决定，不自动替换人工值。
- 产物：把裁决写入项目规划/架构 owner 文档，明确字段枚举、数据保留期、刷新频率、权限和首版非目标。
- 验证：五个问题均有唯一口径，且与真实 TaskRun、权限、数据和公开页面契约无冲突。
- 停止条件：任何答案会改变 owner、数据模型或外部请求权限时，T20-T23 不得开始；不阻塞 T01-T19。
