## 1. 目标与边界

构建一个面向中文用户、支持移动端的私人博客。站点同时支持公开阅读、登录阅读和作者私密记录；普通注册用户只参与阅读、收藏、评论、举报和个人设置，管理员负责站点运营，并可授予或撤销作者身份。

首版不提供公开 API、移动端 API、第三方登录、RSS、点赞或社交平台直发。部署、迁移、Git 提交和推送均仅在用户明确唤起时执行。

### 固定技术方向

- Python 3.12、Django、PostgreSQL。
- Django Templates、HTMX、Alpine.js、Tailwind CSS、TipTap、Markdown。
- Docker Compose：Django/Gunicorn、PostgreSQL、Redis、Celery Worker、Celery Beat、Caddy、Umami、Mailpit。
- `uv` 管理项目依赖；Caddy 提供反向代理与未来 HTTPS。
- Pytest、Playwright、Ruff 分别承担后端、真实浏览器与静态质量验证。

### 不可违反的产品约束

- 站点只有一个管理员账号；管理员同时是作者。
- 文章可见等级为大众、登录、私人。管理员可查看所有文章状态，但查看其他作者内容需通知作者。
- 正文、草稿、版本和权限数据以 PostgreSQL 为准；媒体仅存服务器目录；Redis 只存缓存和短期状态。
- 所有图片统一限制 2 MiB，验证真实格式、去除 EXIF，并保留 GIF 动画；解码安全上限以 `DEC-005` 为准。
- 所有管理员写操作永久审计；运行错误永久保存且脱敏；普通用户只见通用错误和错误编码。
- 代码位于 `/home/code/personal-blog/`；`var/`、`.env`、备份和运行日志不进入 Git。

## 3. 原型先行阶段

原型不接入真实数据库或邮件服务。现有 HTML 用于验证视觉方向和复合信息架构；未单独展示的路由、权限、异常和移动状态由 `page-state-matrix.md` 明确，不能从原型假数据推断业务完成。

### 3.1 原型覆盖的用户流

1. 访客：首页、分区与标签筛选、搜索、文章阅读、目录、分享、登录提醒页、404、主题切换。
2. 注册用户：注册、邮箱验证码、登录双方式、个人菜单、个人主页、收藏、通知、个人设置和会话管理。
3. 作者：文章列表、新建/编辑、格式选择、实时预览、草稿与冲突、发布审查、版本恢复、评论处理、Markdown 导入。
4. 管理员：用户与作者角色、文章查看/隐藏/删除/恢复、评论/举报、通知、邀请码、导航树、站点设置、导出、日志和 Umami 入口。
5. 异常与权限：私人文章、禁用账号、IP 受限、磁盘空间受限、导出进行中、举报结案和删除占位。

### 3.2 原型页面清单

- 公共层：首页、搜索/筛选结果、文章详情、登录提醒、404、关于、友情链接、留言板。
- 身份层：注册、登录、忘记密码、验证码、账号受限提示。
- 个人层：个人主页、设置、会话、收藏、通知页和通知浮层。
- 作者层：我的文章、编辑器、发布审查、版本时间线、评论管理、导入预览和结果页。
- 管理层：用户与 IP 管理、文章操作、举报审核、邀请码、通知管理、导航树、站点设置、日志、导出任务与分析入口。

### 3.3 前端基线验收标准

- 桌面、平板和手机视口均无横向溢出、遮挡或无法触达的主要操作。
- 亮色、暗色、护眼三种模式使用一致的淡杏酒红视觉系统。
- 页面明确呈现加载、空、错误、禁用、权限不足、确认和完成状态。
- 作者与管理员权限差异在界面中可被真实操作路径验证，而不是仅靠文案说明。
- 页面信息架构、导航层级、关键表单和权限状态以架构前端契约与页面状态矩阵冻结；原型演示代码冲突时不得覆盖它们。

## 6. 架构质量硬约束

本项目以长期维护、权限正确性和可扩展性为目标。实现不得为了尽快拼出页面而把领域规则、查询、权限、任务调度和模板逻辑堆进同一个文件或同一层。

### 6.1 稳定领域所有权

详细架构文档将按下列稳定能力建立 Django 应用或等价的清晰模块边界：

| 领域 | 唯一所有者职责 |
| --- | --- |
| `core` | 配置、时区、错误模型、通用但不含业务规则的基础能力 |
| `accounts` | 用户、角色、会话、认证、验证码、禁用和 IP 封禁 |
| `content` | 文章、可见性、分区、标签、版本、草稿、发布、删除和恢复 |
| `media` | 上传校验、目录归属、引用计数/清理、图像处理和访问策略 |
| `comments` | 评论、回复、缓冲、排序、删除占位和留言板复用 |
| `moderation` | 举报、申诉、管理员内容操作、理由、通知与最终裁决 |
| `notifications` | 通知投递、已读状态、聚合、群发和保留策略 |
| `navigation` | 导航树、静态内容页、友情链接和站点公开信息结构 |
| `operations` | 审计、错误日志、备份、磁盘保护、部署状态和任务监控 |
| `exchange` | Markdown 导入、ZIP 导出、预览、冲突处理和归档生命周期 |
| `analytics` | Umami 集成、管理员入口和一月数据保留任务 |

模块之间不得复制权限判断、通知逻辑、图片校验、缓存失效或重试实现。跨域行为必须委托所属模块的公开服务接口，必要时以明确领域事件连接。

### 6.2 分层与依赖方向

- Django 模型负责数据不变量、关系和约束，不承载复杂跨实体流程。
- 应用服务负责命令式业务动作、事务边界、授权、审计和领域事件，例如发布文章、删除评论、审核举报、导入包和禁用账号。
- Repository/查询层封装复杂持久化查询，避免视图或模板散落 ORM 组合。
- Views、HTMX 片段和模板只负责 HTTP/表单转换、展示状态和调用应用服务；不得自行实现权限、事务或任务重试。
- Celery 任务只调度可重入的应用服务，不复制业务规则；每类任务定义幂等键、重试、最终失败与清理语义。
- 权限策略集中于服务端策略对象或领域服务；前端隐藏按钮绝不能成为授权边界。

### 6.3 数据与变更纪律

- 使用规范关系模型、外键、唯一约束、检查约束和针对真实查询的索引；不以无边界 JSON 字段充当关系模型替代品。
- 文章正文、版本、草稿、审计、导入和删除均定义完整生命周期，软删除与物理删除不可混淆。
- 每项迁移先说明前向兼容、回滚限制、备份、锁影响和部署顺序；不得在未授权时对共享数据执行迁移。
- 所有时间以 UTC 存储、以 Asia/Shanghai 展示与计算业务日界；公开标识使用稳定不可变 ID。

### 6.4 可维护性门槛

- 每个稳定能力只有一个主要实现中心；不建立平行的权限、缓存、通知、媒体或任务体系。
- 不创建 `misc`、万能 `utils`、巨型 `views.py`、巨型 `models.py` 或跨领域 service。
- 单文件接近 800 行即复核职责；超过 1,200 行新增独立行为前默认拆分。
- 每个模块拥有同域测试、URL/表单或命令入口、服务层、模板/组件和数据迁移，不让调用方反向访问内部实现。
- 重要跨层动作提供紧凑契约矩阵：用户动作、权限、服务、数据副作用、异步任务、通知、失败状态和测试证据。

### 6.5 质量门禁

- 业务变更默认采用聚焦的 pytest RED-GREEN-回归流程。
- 权限、版本、删除、导入导出、任务和缓存变更必须包含隔离数据库读回验证。
- 可见界面必须使用 Playwright 在桌面与手机视口验证关键真实用户流、空态、错误态、禁用态和权限态。
- Ruff、测试、浏览器验收和容器健康检查未提供新鲜证据时，不宣称模块完成。

## 7. 关键风险与控制点

| 风险 | 控制方式 |
| --- | --- |
| 私人内容与管理员例外越权 | 统一服务端权限矩阵；管理员查看通知作者；前端不承担授权 |
| 导入覆盖、版本和格式冲突 | 导入预览、逐项决策、版本保留、幂等 ID 和部分成功结果 |
| 评论/举报滥用 | 缓冲、冷却、IP 封禁、举报状态机、最终裁决与永久审计 |
| 长期数据膨胀 | 30 天备份、三天导出包、一个月分析数据、媒体清理和磁盘阈值 |
| 异步任务重复或失败 | 幂等键、三次退避重试、最终失败日志与管理员通知 |
| 部署或迁移破坏线上 | 用户显式部署、迁移前备份、健康检查、应用回滚和维护页 |
| 需求漂移 | 访谈记录为唯一真值；原型确认后冻结交互与信息架构，再写详细架构 |
