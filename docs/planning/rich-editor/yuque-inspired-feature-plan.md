# 面向 Kaj 的语雀式富文本编辑能力规划

## 文档定位

这是一份产品与工程复刻规划，不是语雀源码、视觉或商标的复制。功能观察来自语雀公开可访问页面、帮助内容和常见编辑器行为；语雀是闭源产品，无法把内部实现当作本项目的事实。本文只提取适合 Kaj 文章创作的交互原则，并以当前项目的权限、媒体、Markdown 和版本模型重新实现。

目标是把“富文本模式过于简陋”拆成可以逐期交付、可回退、可测试的能力集合。首要标准是写作效率、内容安全、文章发布稳定性和移动端可用性，不是一次性追平语雀全部产品面。

分析口径：2026-08-07 读取语雀公开站点 `https://www.yuque.com` 及公开帮助入口，结合其可观察的 block 编辑、快捷插入、工具栏、目录、媒体和协作产品模式整理。公开页面只能证明用户可见行为，不能证明语雀内部的 schema、服务端实现或授权策略；本文中的工程方案全部以 Kaj 当前代码为准。

## 当前基线

当前编辑器已经有正确的基础，但暴露面仍接近 StarterKit 的最小子集：

- 前端使用 TipTap 3，正文以 `TIPTAP_JSON` 保存，格式在文章工作流中锁定；Markdown 和富文本不能在普通编辑时任意切换。
- 当前工具栏只有粗体、斜体、删除线、二级标题、无序列表、有序列表、引用、代码块、撤销和重做。
- 已有正文图片粘贴上传、图片库、正文图片引用删除、Markdown 文件导入、云端草稿、本地草稿和实时预览定位。
- 服务端 `render_tiptap` 使用固定节点/Mark 白名单和 HTML sanitizer；正文媒体必须是允许的 `media:<ULID>`，不能直接信任浏览器 HTML。
- 文章修订是不可变事实，正文、封面、附件、标签、分区和发布状态由现有 Article/ArticleRevision 所有者管理；富文本扩展不能另建一套文章保存入口。

因此，第一版不应重写编辑器或改成任意 HTML。正确方向是扩展现有 TipTap owner、扩展同一份服务端 schema 和 sanitizer，并让所有新节点都能在预览、发布、文章查看、导入导出和历史版本中得到一致结果。

## 从语雀提取的交互模型

语雀式编辑器的核心不是“按钮更多”，而是把每一段正文当成可移动、可转换、可插入的 block，同时保留选中文字级别的快捷格式。

### 1. 双层工具入口

- 顶部固定工具栏：常用格式、插入、撤销/重做、清除格式和更多菜单，适合明确操作。
- 选区浮动工具条：选中文字后就地提供粗体、斜体、链接、代码、颜色/高亮等，不迫使用户把光标移到顶部。
- 空段落快捷菜单：输入 `/` 或点击 block 左侧加号，按搜索结果插入标题、列表、任务、引用、代码、表格、图片、附件和分隔线。
- Markdown 快捷输入：`# `、`- `、`1. `、`> `、`````、`[] ` 等在输入后自动转换，降低从 Markdown 迁移的成本。

### 2. Block 级编辑

- 每个 block 可以改类型、复制、删除、上下移动和拖拽排序；拖动时整块浮起，其他 block 实时让位。
- 标题、段落、引用、列表、代码、表格、图片和附件都是独立 block，不能用不可见的 HTML 拼接替代。
- 空 block 的行为必须稳定：退格合并、回车创建同类 block、连续回车退出列表/引用、拖动和撤销后光标位置可恢复。

### 3. 内容表达能力

语雀公开体验中最有价值的能力可归为以下几组：

| 组别 | 目标能力 | Kaj 适配判断 |
| --- | --- | --- |
| 文字 | 段落、H1-H6、粗体、斜体、删除线、下划线、行内代码、链接、硬换行、清除格式 | 必做；可直接扩展当前 TipTap schema |
| 结构 | 无序/有序列表、任务列表、引用、提示块、分隔线、折叠内容 | 必做其中前五项；折叠内容后做 |
| 程序 | 代码块、语言选择、复制代码、等宽行内代码 | 必做；高亮先使用受控语言集合 |
| 数据 | 表格、表头、单元格合并/拆分、增删行列、表格复制粘贴 | 必做基础表格；复杂合并作为增强项 |
| 媒体 | 图片上传/粘贴/拖入、替代文本、尺寸、附件卡片、链接卡片 | 必做，复用现有媒体与附件权限 |
| 嵌入 | Bilibili 等可信来源卡片、不可用来源的明确降级 | 只开放既有可信来源，不做任意 iframe |
| 导航 | 标题大纲、文档目录、块链接、锚点 | 必做大纲；块链接和自动目录后做 |
| 协作 | 评论、选区评论、版本历史、恢复 | 版本与文章评论复用现有能力；实时协作暂不做 |
| 智能 | AI 续写、改写、总结、翻译 | 暂不纳入首期，避免外部模型、隐私和费用边界失控 |
| 扩展 | 白板、流程图、思维导图、数据库表格、第三方插件 | 不作为首期目标；以可信卡片接口预留扩展点 |

## Kaj 的目标编辑体验

### 工具栏分组

工具栏按写作频率分层，而不是把所有按钮平铺：

1. `文本`：段落/标题选择、粗体、斜体、删除线、下划线、行内代码、清除格式。
2. `插入`：链接、图片、附件、引用、提示块、分隔线、代码块、表格、任务列表。
3. `编辑`：撤销、重做、复制当前块、删除当前块。
4. `更多`：高亮、上标/下标、对齐、语言选择、块链接和嵌入。

窄屏只保留高频按钮和一个“更多”菜单；按钮必须有图标、可见焦点、`aria-label` 和悬停说明，不能用一排文字按钮挤压编辑区。

### Slash 菜单与 Block 菜单

- `/` 后出现可搜索菜单，显示图标、名称和一句用途说明；输入继续过滤，方向键选择，Enter 插入，Escape 关闭。
- 左侧 block handle 只在当前段落或悬停时出现，点击可打开同一份插入菜单；拖动手柄和菜单按钮必须是两个明确的命中区域。
- 菜单插入失败时不改变正文；上传中的图片/附件以临时节点显示，失败自动移除并保留可重试提示。

### 选区浮动工具条

选中文字后显示粗体、斜体、删除线、下划线、行内代码、链接和高亮。链接使用小型对话框确认 URL、标题和是否移除；不直接把用户输入的 HTML 写入正文。浮动条不得遮挡选区、键盘焦点或移动端输入法。

### 大纲与定位

编辑区旁显示 H1-H6 大纲，点击滚动到标题；标题变化实时更新。大纲只从合法 heading 节点生成，不把用户正文当作 HTML 查询。预览继续跟随编辑光标，首屏内容不足时从顶部开始，避免当前已有的空白定位问题。

## 内容契约与数据设计

### Canonical source

TipTap JSON 仍是富文本的唯一编辑源，Markdown 仍是 Markdown 文章的唯一编辑源。预览、发布、文章查看和导出都调用现有 `render_tiptap`/`render_markdown` owner，不在模板或前端另写渲染器。

建议保留当前 revision 结构，并以兼容扩展方式增加节点：

```text
doc
  paragraph | heading | blockquote | bulletList | orderedList
  taskList | codeBlock | table | image | attachment | callout
```

所有节点必须有明确 attrs 形状。媒体节点只保存 `media:<ULID>`、alt、title 和经过约束的展示尺寸；附件节点只保存 `media:<ULID>`，不能保存客户端路径或任意 URL。链接只保存 href/title，服务端重新校验协议和外部链接策略。

服务端建议增加一个明确的富文本 schema 版本 owner（优先作为 ArticleRevision 的版本字段，而不是向正文 JSON 塞任意顶层字段）。渲染器按版本选择允许节点，旧版本继续可读，新版本不能让旧文章失效。迁移采用 expand/migrate/contract：先扩展可选 schema 和 renderer，再由编辑器产生新节点，最后才考虑收紧旧节点。

### 首批 TipTap 扩展候选

实现前逐个核对锁文件、许可证、包体积和服务端对应 schema，不直接把浏览器扩展的默认 HTML 当成后端契约。候选包括 `Underline`、`Link`、`Highlight`、`TaskList/TaskItem`、`Table/TableRow/TableHeader/TableCell`、`TextAlign` 和受控的代码语言选择。`Image`、附件、提示块和可信嵌入应由 Kaj 自有 extension 所有者实现，以接入现有媒体权限和 `media:<ULID>` 语义。

### 服务端渲染同步清单

每增加一种 node/mark，必须同时更新：

- TipTap 前端 schema、JSON 归一化和 toolbar active 状态；
- `apps/media/rendering/tiptap.py` 的结构白名单、attrs 校验和 HTML 输出；
- `html_policy.py` 的标签、属性、协议和媒体 allowlist；
- 文章预览、发布、公开查看、版本预览、导入导出和缓存 key；
- 节点/属性错误测试、未知节点拒绝测试、跨角色媒体权限测试；
- 编辑器真实浏览器流和移动端布局。

不允许“前端能编辑、服务端只能丢弃”或“预览能显示、发布后变空”的静默降级。

## 分期实施路线

### R0：契约与编辑器骨架

先建立节点/Mark 表、schema 版本、渲染快照和错误码；把工具栏按钮改为分组、overflow 和统一 command registry。补齐焦点、选择、撤销、重做和 pending 上传状态的测试。停止条件是旧 Markdown/旧 TipTap 文章读写不变，未知节点会明确 422。

### R1：高频文字格式

交付段落/H1-H6、下划线、行内代码、链接对话框、清除格式、选区浮动工具条、Markdown 快捷输入和完整键盘快捷键。链接仅允许 `http`、`https`、`mailto` 与项目认可的 `media` 协议；外链统一安全打开。

### R2：Block 操作与结构块

交付 `/` 菜单、block handle、拖拽排序、任务列表、提示块、分隔线、代码块语言选择、复制代码。保证回车/退格/合并/拆分/撤销后的光标稳定，拖动中不出现虚线闪烁或位置争夺。

### R3：表格与媒体工作流

交付基础表格（插入、增删行列、表头、复制粘贴）、图片拖入/粘贴/替换/alt、附件卡片和上传进度。附件严格复用现有作者授权、单文章一个附件、格式和 10MB 限制；未授权用户只能看到真实的无权状态。

### R4：大纲、嵌入与阅读一致性

交付标题大纲、点击定位、自动目录候选、可信来源嵌入卡片、嵌入失效降级、正文与预览的滚动同步。公开查看、搜索摘要、版本预览和导出必须输出同一语义结构。

### R5：文章工作流增强

把现有云端草稿、本地草稿、版本历史、冲突解决、评论和发布审查接入 block 级变更摘要；支持块复制、块删除和版本恢复后的媒体清理检查。实时多人协作、AI 和白板另立项目，不阻塞前五期。

## 权限、媒体和安全边界

- 编辑权仍由 authoring/content owner 判断；隐藏按钮不能替代服务端授权。
- 图片和附件上传仍经 media owner，文件类型、大小、路径、归属、清理和绑定关系在服务端裁决。
- 图片只能引用当前账户/文章允许的媒体 ID；删除正文图片必须同时处理服务器文件和正文引用的状态差异。
- 嵌入仅允许项目配置的可信来源；不接受任意 iframe、`javascript:`、带凭据 URL 或服务端抓取外部 URL。
- 代码块只渲染文本，不执行代码；语言标识是受控枚举，不加载远程高亮脚本。
- 表格单元格限制深度、节点数、文本长度和嵌套复杂度，避免 JSON 炸弹和渲染阻塞。
- 预览失败保留用户输入并给出可执行错误；不能以空正文、旧预览或假成功掩盖失败。

## 验收矩阵

### 功能

- 工具栏、选区菜单、`/` 菜单和 block 菜单可用鼠标、键盘和触控操作；所有 command 有 active/disabled 状态。
- 文字、结构、表格、代码、图片、附件、链接和嵌入在编辑、预览、保存、发布、历史版本和公开查看中保持一致。
- 粘贴纯文本、Markdown、富文本 HTML、图片和附件时都有明确成功、失败、取消和重试状态；不会丢失当前光标或未保存内容。
- 自动保存、冲突、刷新、返回和发布失败后，正文、媒体引用和滚动位置可恢复。

### 安全与数据

- 未知 node/mark、非法 attrs、超限文档、未知媒体、越权附件和危险链接均被服务端拒绝。
- 旧文章和旧版本不需要回填即可继续渲染；新节点缺少渲染器时阻断保存，不静默删除。
- 保存成功后通过数据库读回 revision JSON、媒体绑定、附件引用、缓存 key 和审计结果。

### 视觉与可访问性

- 串行验收 390、768、1440 三个视口；工具栏、浮动菜单、表格和代码块无横向溢出、重叠或按钮挤压。
- 键盘覆盖 Tab/Shift+Tab、Enter、Escape、方向键、快捷键、菜单循环焦点和对话框返回焦点；触控目标不小于 44px。
- 检查默认、展开、上传中、失败、无权、空正文、长标题、长代码、宽表格和 reduced-motion 状态。

## 明确不照搬的部分

首期不做语雀级实时多人协作、多人光标、AI 生成/改写、白板/思维导图、任意第三方插件、复杂数据库表格、音视频编辑和服务端抓取式链接卡片。这些能力会显著扩大权限、存储、任务、外部服务、费用和隐私边界；需要单独的架构评审和授权，不能作为富文本工具栏的顺手扩展。

## 推荐首期范围

R0-R2 是最适合 Kaj 的第一版：分组工具栏、选区浮动格式、标题级别、下划线/行内代码/链接、Markdown 快捷输入、`/` 插入菜单、block 拖动、任务列表、提示块、分隔线和代码语言选择。它能解决“按钮少、结构编辑困难、格式操作慢”的核心问题，同时复用当前 TipTap、媒体上传、草稿、预览和发布链路。

表格、附件卡片、图片尺寸和大纲进入 R3-R4；协作、AI 和复杂扩展保持独立立项。每一期先做 RED/GREEN 的 schema 与服务端渲染测试，再做真实浏览器流，最后才扩展视觉细节。
