# 正式状态修正 Runbook

本文件用于本次候选上线前处理已知的历史异常，不是自动迁移脚本。执行前必须取得生产部署和生产数据修正授权。所有命令都必须限定到正式项目服务、正式数据库和当前候选版本；禁止连接 Labs 或使用宽泛的 `UPDATE`/删除语句。

## A. 快照与停止门禁

1. 记录候选 SHA、当前应用镜像、服务 PID/工作目录、数据库连接健康、Redis 健康、Outbox 传输配置状态和 Beat 最近触发时间。
2. 只读统计 `OpportunityCheckRun` 的 `PENDING/RUNNING/CANCEL_REQUESTED`、来源 `RUNNING`、`TaskRun` 的 `running/retry_wait` 和 Outbox 的 `PENDING`/租约到期项；输出只包含数量、稳定 ID、状态和错误码。
3. 若数据库连接、备份、服务身份或对象归属无法确认，立即停止，不改变任何行。

## B. 招聘检查孤儿运行

1. 确认候选 Worker 已健康、数据库连接已恢复，且不会同时启动第二个恢复批次。
2. 通过现有任务入口 `apps.opportunities.recover_check_leases` 执行一次有界恢复；不要直接调用 adapter `collect()`，不要手工把运行标为成功。
3. 读回每个受影响的 `TaskRun`、`OpportunityCheckRun` 和来源明细：过期租约清零；来源 `RUNNING` 回到 `PENDING`、`FAILED` 或 `NOT_EXECUTED`；领域运行进入正确终态；需要重试的任务已重新派发。
4. 再运行只读不变量检查：没有已过期的活动租约、没有终态 TaskRun 绑定活动领域运行、没有活动运行被错误的旧幂等键永久复用。
5. 若发现未知任务名、多个领域运行无法安全归属、状态互相矛盾或恢复后仍有孤儿行，停止并保留审计证据；不删除、不覆盖、不强制成功。

## C. `publish_outbox` 失败积压

`core.outbox_transport_failed.v1` 表示批次中的 transport 发布失败并进入延迟重试，不等价于业务事件已经丢失。先定位依赖故障，再使用现有发布 owner 重试。

1. 只读确认 Outbox transport 工厂、通知/邮件依赖、数据库连接、DNS/TLS 和网络出口状态；日志只记录脱敏错误码和 trace code。
2. 读取失败事件的数量、最早 `available_at`、尝试次数、事件类型和租约状态；不要读取或输出事件正文、邮箱、token 或连接串。
3. 依赖恢复后，以默认有界批次调用现有 `publish_outbox`/`publish_batch` 入口一次，确认 `claimed/published/failed` 结果，并等待租约释放。
4. 读回成功事件为 `PUBLISHED` 且 lease 为空；仍失败的事件保留稳定错误码和下一次可用时间，交给既有重试/告警，不手工清除。
5. 对可能产生外部副作用的事件，确认 consumer 的幂等记录和去重键；不能证明幂等时停止重试并升级人工审查。
6. 连续三次仍失败、失败量增长、出现重复通知或 transport 返回未分类错误时，停止发布，保留备份和日志证据，修复依赖后再开新的授权窗口。

## D. 恢复后的调度读回

1. 确认每分钟补偿任务可以扫描 `PENDING`，每日上海时间 18:00 的 Beat 任务使用当天窗口的幂等键。
2. 不手动抓取来源；等待一个受控调度窗口或在另一个明确授权的演练环境验证派发。
3. 记录恢复前后计数、任务 ID、稳定错误码、Outbox 发布结果、通知去重结果和健康检查，不记录正文、邮箱或凭据。

## 回滚与停止

恢复发现错误时，只停止本次候选 Worker/Beat 的进一步派发并回退应用镜像；本轮没有数据库 migration，不执行反向迁移。数据库备份、旧镜像和状态审计记录必须保留，任何人工数据修正都要另行审批。
