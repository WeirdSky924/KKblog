# P1：隔离环境全链路性能与容量任务

状态：未执行

目的：在 Labs/预发布的真实 PostgreSQL、Redis、Celery、媒体和 Mailpit 环境中，测量系统在代表性数据规模下的稳定并发、查询性能、队列吞吐和文件 IO 上限。

## 1. 前置数据与工具

- [ ] 使用脱敏数据库快照，不能连接正式数据库。
- [ ] 准备代表性数据：文章/修订/标签/评论、作者、通知、岗位/来源/筛选项、知识文档/题库/答题记录、媒体和导出包。
- [ ] 记录数据规模、最大正文、最大标签数、岗位总数、题库题数、媒体总量。
- [ ] 选择一种受控压测工具（k6、Locust 或 Gatling），固定并发、速率、连接复用和请求超时。
- [ ] 使用本地 Provider mock/replay 验证 AGENT 控制面，不消耗真实模型额度。
- [ ] 监控 PostgreSQL、Redis、Celery、文件系统、容器资源和应用 trace。

本任务对应执行日志：[p1-preproduction-load.execution.md](p1-preproduction-load.execution.md)。每次执行先生成唯一 `run_id`（建议 `P1-YYYYMMDD-HHMM-序号`），固定数据快照和压测脚本版本；执行日志只追加真实结果，不覆盖历史批次。

## 2. 流量模型

初始混合比例可作为起点，正式比例需按真实访问日志校准：

- 40% 公开阅读：首页、文章列表、文章详情、作者页。
- 20% 找工作：搜索、筛选、分页、岗位详情。
- 15% 账户与互动：登录、通知、收藏、点赞、评论读写。
- 15% 知识学习：文档/题库/答题记录读取和答题提交。
- 10% 管理与任务：分页查询、审核队列、任务历史、状态轮询。

执行梯度：

- [ ] 基线：1、5、10 并发。
- [ ] 阶梯：25、50、100 并发，达到每档稳定后再升档。
- [ ] Spike：短时间达到稳定并发的 2 倍，再观察恢复。
- [ ] Soak：稳定负载 4 小时，观察内存、连接、队列和缓存增长。
- [ ] Stress：只在隔离环境持续加压到 SLO 失效，记录安全拐点。

每一档必须记录：并发或 RPS、连接复用、请求超时、随机种子、场景比例、预热时长、稳定窗口、最大请求数和停止条件。没有这些参数的结果只能作为观察记录，不能作为容量结论。

## 3. 数据库与缓存任务

- [ ] 对文章、作者、岗位、通知、题库、错题本和任务历史分页查询做 p95/p99 测量。
- [ ] 对岗位搜索/筛选/发布时间排序执行 `EXPLAIN` 和不同数据量对比。
- [ ] 对并发写入执行评论、收藏、点赞、答题保存、配置版本冲突。
- [ ] 测试 `select_for_update`、`SKIP LOCKED`、唯一约束、幂等键和死锁恢复。
- [ ] 记录数据库连接池、锁等待、慢查询、WAL、autovacuum、缓存命中率和膨胀。
- [ ] 测试 Redis 限流、缓存失效、热点键、断连、重启和内存压力。

查询性能必须保存脱敏的 `EXPLAIN (ANALYZE, BUFFERS)` 摘要、数据规模、索引版本和采样时间；不得把整段正文、用户令牌或连接串写入报告。并发写入必须记录成功、冲突、重试、死锁和最终读回数量。

## 4. Celery、Outbox 与 IO 任务

- [ ] 测量 Outbox 发布、Consumer 去重、通知聚合和告警邮件吞吐。
- [ ] 测量招聘检查派发、来源串行处理、租约恢复和历史清理。
- [ ] 测量导入、导出、备份、媒体上传/下载/删除和 ZIP 解压。
- [ ] 对大文件、并发上传、文件系统低容量和只读错误执行隔离测试。
- [ ] Worker 数量、并发、prefetch、任务超时和重试策略逐项记录。
- [ ] 记录任务等待时间、执行时间、重试、最终失败、租约过期和重复执行。

任务与 IO 结果按 `queued_at → started_at → finished_at` 计算等待和执行耗时，并记录幂等键、最终状态、重试次数、失败码、临时文件清理和数据库读回；不以“任务被派发”代替“任务完成”。

## 5. 通过标准

- p95/p99、错误率、队列等待和资源使用满足预先设定的业务 SLO。
- 压测结束后连接、队列、租约、临时文件、Redis 键和测试数据回收。
- 数据库没有未处理死锁、长事务、重复事实或不可解释的锁等待。
- Outbox、任务、通知和媒体状态最终一致，失败任务可恢复且不重复产生副作用。
- 产出稳定并发上限、推荐并发上限、单机资源上限和下一步优化项。

通过/失败阈值须在执行前写入执行日志，包括 p95/p99、错误预算、队列等待、数据库锁等待、连接峰值、内存/Swap、磁盘余量和恢复时限。发现瓶颈时先建立带证据的优化任务，再决定是否提高下一档负载。
